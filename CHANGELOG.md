# Changelog

All three packages, `@agent-custody/receipts`, `@agent-custody/state`, and `agent-custody` on PyPI, move in lockstep. The receipt format has stayed at v0.2 throughout; every addition to it is an optional field, so earlier receipts and the published conformance vectors remain valid.

## Unreleased

- **The anchor: the log's checkpoints on a chain (issue #176).** `agent-custody anchor` watches a log's published checkpoints and proves that each new one extends the last one it anchored, refusing with an alarm when it does not. When any log moved, it commits a Merkle root over every watched log's checkpoint (the new one, or the last one anchored) in one zero-value transaction from its address to itself, and writes each log's record (its own checkpoint, the transaction, and its inclusion proof) to a directory to serve read-only. The chain is Ethereum mainnet by default; `--chain` picks `base`, `arbitrum`, `optimism`, `polygon`, or any EVM chain by its id, and a verifier names the same chain with `--anchor-chain`. It sends nothing when no log has grown, skips a run whose fee per gas is above `--max-fee-gwei` (a default per named chain: 20 gwei on Ethereum, 1 on the L2s, 1000 on Polygon; required for a chain given by id), and holds a transaction in flight before sending another. A transaction stays pending until its block is finalized: a reorg that moves it rewrites the records, and one that drops it sends the same root again. `log-check --anchor-url --anchor-address --anchor-rpc-env --anchor-log-id <tenant>=<id>` checks the record against one or more JSON-RPC endpoints, which must agree: the sender, the calldata, the inclusion proof, success, and finality. It requires the anchored checkpoint and the head to name the pinned log id, and the record's transaction to be the newest from the address by its transaction count, so an older record or another tenant's cannot stand in. It also checks that the head extends the anchored checkpoint, and that a head ahead of its anchor is not left so for longer than `--max-anchor-lag` by the anchor's block time, so a rewritten or rolled-back tree is caught from the chain alone. The key and endpoint come from the environment; signing needs the optional package `viem`, and checking needs no Ethereum library. `docs/anchoring.md`, example 33.

## 0.10.0 — 2026-10-23

- **Fix: the memory server and the review console stop on SIGTERM (issue #148).** `agent-custody-memory serve --http` and `agent-custody-memory review` waited for SIGINT only, so a container runtime, systemd or Kubernetes stopped them with SIGKILL after the grace period. They now close and exit 0 on SIGTERM. The memory server over HTTP answers GET with 405, because its held SSE stream kept a connected gateway from letting the stop finish, and it cuts the connections that remain 3 seconds after the stop starts. It closes the ledger before it exits.
- **Fix: a log outage after an ordinary call keeps its receipt (issue #149).** Before, when the log did not take the receipt of a call that the gateway had already forwarded, the agent got an error and the receipt was lost, so a model could repeat a refund. Now the gateway keeps the signed receipt and its salts in `receipts/outbox/<id>.json` and returns the real outcome with `_meta["agent-custody/log-pending"]: true` (`LOG_PENDING_META_KEY`). A serving gateway (`gateway` over stdio, `--http`, or `--a2a`; the option `autoFlush`) appends the outbox at start and every 30 seconds (`GatewayHost.flushOutbox()`), oldest statement first, and writes the bundle when the log takes it; `check` and `reconcile` never flush. A lock file in the outbox keeps several gateways on one `receipts/` directory from appending a receipt twice, and the log's answer is recorded in the entry before the bundle is written, so a failed bundle write does not append the leaf again and is printed on stderr. An entry that another key signed stays in the outbox and is reported, not renamed. The entry is synced to disk before the agent gets the result. `close()` waits for a flush that runs. `GET /health` reports `pendingReceipts`. A `precommit` tool is still withheld when its authorization is not logged, and a financial operation keeps the old order. With a remote log and an empty `precommit`, the gateway prints a warning at startup; `"requirePrecommit": true` makes it a startup error. `docs/usage.md` has a table of each log failure for each kind of tool.
- **Fix: `policy simulate` skips a reconciliation receipt.** A reconciliation receipt is a provider read, and no policy ran for it. A replay evaluated it as a second `stripe.refund` call, so a tighter refund policy reported a false `allow -> deny` change and counted the refund two times. The replay now counts such a receipt in the new report field `reconciliations`. It does not count it in `evaluated` or `skipped`, so the report stays complete. `formatSimulation` prints the count. The console's simulate response and page show the count too. A reconciliation whose original receipt is missing is a skip, so the report says `INCOMPLETE`. The library treats a predicate as a reconciliation only when a gateway issued it and its operation names another receipt; it trusts the receipt only after `verifyBundle`.
- **Fix: the `verify` text report shows a reconciliation receipt as a provider read.** The `policy` row says that no policy was evaluated, and the `execution` row starts with `provider read`. The browser verifier prints the same rows. Before, the report printed `policy observed allow` for a receipt whose reasons say that no policy ran. No check changes.
- **Gateway: reload the Cedar policy without a restart (issue #145).** The gateway re-reads `policyFile` whenever it changes (device, inode, mtime, ctime, or size, and on each call while the file is under two seconds old), as it does `revokedGrants`, and evaluates the next call under the new policy, for stdio, HTTP, A2A, and observe mode, with no dropped session. A call already evaluating finishes under the policy it started with, and its receipt carries that digest. A changed file that does not parse, or cannot be read, is refused: the policy in force stays, never an allow, and `POLICY NOT RELOADED` goes to stderr. Each change and refusal is appended to `receipts/policy-reloads.jsonl` with the time and both digests. `GatewayHost.policyDigest()` returns the digest in force. The console no longer tells the operator to restart after a save.
- **Fix: `policy simulate` checks the receipt id against the file name.** A receipt copied over the file name of another receipt hid that call, counted the copy two times, and the report still said `COMPLETE`. The command now fails when `<id>.json` holds a receipt with another id, as it already does for an authorization file. A test also checks that `simulatePolicy` evaluates each receipt before it pulls the next.

## 0.9.0 — 2026-10-21

- **State:** a live Codex support recovery demo (example 10; guide `docs/codex-recovery.md` in the receipts package). A Codex agent works through the gateway and writes a wrong benefit and a credit, because of a wrong CRM plan. The operator corrects the plan. `inspect` traces the blast radius and plans the retractions, the corrective writes, and the credit reversals. `recover` runs the plan only with an approval that equals the digest of the saved plan, and `verify` checks the stores against the receipts. `inspect` refuses a credit or a current benefit that no memory read supports, because the demo cannot decide its recovery. After a partial recovery, a refreshed plan lists the corrective writes again.
- **State, breaking for custom stores:** `Store.remove(externalId, fact)` is now `delete(entry)`, and `verifyRemoved(externalId, fact)` is now `verifyDeleted(entry)`, where `entry` is a `StoreEntry { externalId, factId, text, storedAt? }`. `createMemoryServer` refuses a store that has no `delete`. A store written for the earlier interface therefore fails at startup. It is never called with an entry where it expects an id, so its old check can never certify an erasure that did not happen. The adapters in this package are changed already. `entryOf(fact, externalId)` builds an entry from a fact.
- **State:** the repair sweep (issue #107). A write reaches the stores before the ledger, so a failed ledger append leaves store entries that the ledger has no fact for. `memory.repair` and `agent-custody-memory repair --via <gateway.json> --reason <text>` find those entries through the new optional `Store.list()`, which every adapter implements. The sweep removes each entry that is more than ten minutes old, verifies the removal, and records a `repair` ledger event under the entry's fact id. The ledger records the event before the sweep removes the entry, so the first record of a fact id wins: `Ledger.assert` refuses a fact id that has a repair event, and `Ledger.repair` refuses one that has an assert or returns the event that the entry already has (within one server process). One `memory.repair` runs at a time in a server process. Each store entry records `storedAt`. A write whose stores take more than five minutes is refused before its ledger append, so the entry of a write in progress is not old enough to repair. If the ledger append stalls for longer, the first record wins and the other fails with an error. This holds within one server process. For servers that share a Postgres ledger, an append that stalls after its check can still land after a repair. Example 09.
- **The gateway console.** `agent-custody console --config gateway.json` is an admin service for the person who runs a gateway, separate from the gateway and behind a token read from the environment: the config, the upstreams and tools, the config check, the newest receipts with a verdict each, a policy editor that validates and replays the recorded calls against the proposed policy before it saves (the old version is kept, a stale edit is refused, and the change is audited), grant inspection and revocation, and the audit trail. It holds no principal key and signs nothing; its page writes every value with `textContent` under a hash-only content-security-policy. The gateway image runs it with `console` (compose profile `console`), with its token as a container secret that only the console service holds and the same user as the gateway. A saved policy is guarded: a permit rule with no action and no condition, which a replay of past calls cannot show, needs confirming, and the digest check, the history copy, and the write happen under one lock. The console does not hold the gateway's credentials, so it does not check them or start upstreams that need them, and a connect check that runs too long is cancelled and closes what it started (`createGatewayHost` takes a `signal`). Tutorial 32; `docs/console.md`.
- **Docs and tooling: configuring the gateway.** `docs/configuration.md` is the map of what is configured where (the grant, the Cedar policy, `gateway.json`, the credentials), how a call is decided, tool naming, a worked example with two agents on one shared gateway and four kinds of upstream, how the config works in the Docker image, and a table of startup errors. A test checks that its example config parses, that its policy parses, and that the policy does what the prose says for each agent. `agent-custody check --config gateway.json [--connect]` finds what a config would fail on at startup before it starts: unknown keys (a typo such as `precomit` was silently ignored), a policy that does not parse, missing credential variables or stdio commands, paths that cannot be written, an expired grant, and, with `--connect`, two upstreams offering one tool and tool names that no upstream offers. `GatewayHost.tools()` lists the tools the upstreams offer. The gateway image runs the check on every start and does not start on an error (`GATEWAY_CHECK=advisory` or `off` to change that). `deploy/gateway/example` is a config directory to copy (a REST API, a policy, a fact lookup, `precommit`), with the steps to make the principal's key and issue grants; a test copies it, drives it against a stand-in API, and checks that the policy, the fact lookup, and the grant scopes refuse what they should. The configuration guide says how to make, keep, distribute, rotate, and replace the principal's key: the private half stays where grants are issued, and the gateway holds only the public half. `check` also reports a REST tool with `idempotencyHeader` and no `operations` entry, which makes every call to it fail. An unknown config key, and a `precommit` name that no upstream offers, are errors, so `check` exits 1 for them; a `permit(` in a comment does not count as a permit rule; the Splunk and OpenTelemetry credentials and the operations database and approvals directory are checked. The example and guide policies bound a refund amount from below, and the example says what a retry does without `operations`.
- **Deploy: the gateway as a service.** `deploy/gateway` is a container image, compose file, Kubernetes manifests and systemd unit for one shared gateway that every agent on a host or cluster connects to, each with its own grant. The `gateway-image` workflow builds it for amd64 and arm64 and pushes `ghcr.io/svayatta/agent-custody-gateway`: `edge` and `sha-<short>` on every merge to main, `<version>`, `<major>.<minor>` and `latest` on every release. Every build is smoke-tested before it is pushed. `init` writes a starter config, an example policy, and a demo grant.
- **Deploy: a release deploys the release.** `upgrade.sh` checks out the tag `v<version>` before it deploys, so the compose file, the Caddyfile, and the scripts on the host are the released ones and not main's, and it restores the previous checkout on a rollback. The `AGENT_CUSTODY_VERSION` defaults in the compose files, the Dockerfile, `.env.example`, and the Kubernetes manifest, and the monitor's pinned version, are checked against the package version on every pull request and again on the release tag. A pull request that touches `deploy/` builds the log image from the workspace package, starts it, and checks the compose files, the manifests, the scripts, and `upgrade.sh` against a throwaway repository.
- **Supply chain: signed, attested, pinned.** Every pushed image (log and gateway) carries a provenance attestation and an SBOM and is signed with cosign, keyless; the digest of each release is in the workflow's step summary. Base images are pinned by digest, third-party GitHub Actions by commit, and bun by version, with Dependabot proposing updates. The monitor runs the pinned release, not `@latest`.
- **Fix: long-running services stop on SIGTERM.** The gateway, log, signer, portal and witness waited for SIGINT only, so a container runtime, systemd or Kubernetes stopped them with SIGKILL after the grace period. They now close and exit 0 on SIGTERM.
- **Receipts:** enterprise identity for the hosted portal (issue #115). Roles: each member of a tenant is `owner`, `admin`, `reviewer`, or `readonly`. `readonly` reads, `reviewer` also publishes and removes policy versions, `admin` also manages API keys, invites, and members below owner (never an owner, never granting `owner`), and `owner` also manages billing. A write route that no role table lists needs `admin`. The last owner cannot be removed or demoted. New routes: `GET` and `POST /api/members`, `POST /api/members/<userId>/role`, `POST /api/members/<userId>/remove`, `POST /api/invites/remove`, and `POST /api/invites/accept`, which needs a verified address and allows one tenant per account. `/api/me` returns `role`, `mfa`, and `invites`. MFA: an account can turn on a time-based one-time password (RFC 6238, 6 digits, 30 seconds) with `POST /api/mfa/setup`, `/api/mfa/enable`, and `/api/mfa/disable`. `POST /api/login` then answers `{ "mfa": true }` with a five-minute `custody_mfa` cookie and no session, `POST /api/login/mfa` finishes the sign-in, and GitHub and Google sign-in go through the same code step. A code works once, and wrong codes are throttled per address and per account. `agent-custody log-admin --db-env NAME user mfa-reset <email>` turns MFA off for an account that lost its authenticator. `user mfa-reset`, `sso set`, and `sso remove` write the same audit entry as the other `log-admin` commands (`user.mfa-reset`, `sso.set`, `sso.remove`, with the actor `cli:<user>@<host>`; never a secret). Single sign-on per tenant, set by the operator with `log-admin sso set|show|remove`: OIDC (authorization code with PKCE; the `id_token` signature is checked against the IdP's key set, RS256 and ES256 only) or SAML 2.0 (service-provider initiated, signed assertions required, through the optional peer dependency `@node-saml/node-saml`, loaded when first needed). An IdP is trusted only for its tenant's email domains, and a domain belongs to one tenant. A sign-in creates or links the account, joins it to the tenant with the default role (an unverified password account with that address is deleted with its password, sessions, memberships, and linked providers, whether or not it created a tenant, so a squatter cannot lock the member out; a member that an admin removed rejoins through single sign-on only after a new invite), and skips the portal's MFA, because the IdP owns it. With `--enforce`, members cannot sign in by password, GitHub, or Google, their older sessions end, and invites are refused. Routes: `GET /auth/sso?email=`, `GET /auth/sso/<tenant>`, `GET /auth/sso/<tenant>/callback`, `GET /auth/sso/<tenant>/saml` (metadata), and `POST /auth/sso/<tenant>/saml/acs`. New module `src/sso.ts`, example 31, and the Dockerfile installs `@node-saml/node-saml@5` beside `pg`. The gateway kill switch was already covered: `agent-custody revoke` and `revokedGrants` (example 27); a test now also shows that another agent continues after one agent's grant is revoked.
- **Supply chain: cosign 3 signs the images.** The image workflows install cosign with `sigstore/cosign-installer` v4, which installs cosign 3. An image signature is now a Sigstore bundle, kept as an OCI 1.1 referrer of the image. Verify an image with cosign 3 or later.

- **State: the review console and offline case files (issue #113).**
  - **Review console:** `agent-custody-memory review --receipts <dir>` serves an index of receipts with search by transaction and customer id, or writes a static copy with `--out`. A record that cannot be verified, or whose file name does not match its receipt id, is listed as NOT VERIFIED with the reason, never left out.
  - **Case files:** `review --case <id>` exports one receipt as a case file (`.case.json` or a self-checking `.case.html`), with the ten answers about the call. `review --verify-case` checks either form against independently supplied keys, including `--approval-key` for human-approved calls. It reads a file as JSON only when its name ends in `.json`, and requires a page to be exactly what its case data renders.
- **Receipts, verifiers:** both verifiers now refuse, in `structural parts in clear`, a receipt without its policy digest, an authorization without its proof and tree head, or an attested principal without its key id. No receipt the code produces lacks them; four vectors cover the refusals.
- **State: a live Codex support recovery demo.** Example 10 and `examples/codex-recovery/` let a Codex agent make a wrong refund decision on a stale belief. They then show the operator's recovery: revoke, inspect the blast radius, retract, write the corrected values, reverse the credit, and verify. The tests drive it with scripted calls and never call a model.
- **Docs: the architecture guide** (`site/guide/architecture.md`): what runs on the customer's side and what the hosted log holds, the data model, and sequence diagrams. It states that no independent witness runs for the hosted log yet.
- **Release:** the image and MCP Registry jobs wait until npm serves the released version, so they no longer race the publish.

## 0.8.0 — 2026-10-19

- **Receipts: human approvals (#111).** `approvals` in the gateway config names tools that need a signed, unexpired, single-use human approval, in every mode.
  - **Binding:** the approval is bound to the principal, the agent, the tool, the amount, the currency, the beneficiary, and a digest of every argument. One or two distinct approvers are required, and `maxLifetimeSeconds` caps the lifetime (default 3600).
  - **Single use:** consumption is atomic in a `usedDir` that gateway processes share across restarts.
  - **Checked again before forwarding:** expiry or revocation during fact lookups or precommit refuses the call with a signed receipt.
  - **Evidence:** receipts and precommit authorizations carry the approval, and both verifiers check its signatures (`--approval-key`), validity window, payload binding, consumption, and precommit consistency.
  - **Privacy:** under a private capture rule the approval envelope is withheld unless every argument is in clear and the tool name is not masked. A refusal carrying a valid approval still verifies.
  - Tutorial 30.
- **Receipts: financial operations (#112).** `operations` in the gateway config makes tools financial.
  - **No second execution:** each call keeps one caller-chosen operation UUID, sends the provider an idempotency key, and reserves its amount against a daily budget in SQLite transactions shared across processes. A retry or a restart never forwards a second payment.
  - **Outcomes:** submitted, pending, unknown, confirmed, or failed, recorded apart from execution.
  - **Reconciliation:** `agent-custody reconcile --config gateway.json --operation <uuid>` (`GatewayHost.reconcile`) reads the provider's record and closes an unknown or pending outcome with a signed reconciliation receipt. A call the gateway can prove it never sent is closed and its reservation released. Recovery identifies a dead creator by PID and start time, and the authorization save refuses a call that recovery has closed.
  - **Verification and export:** both verifiers check the operation linkage, and OTel, Splunk, `explain`, and `review` mark reconciliations.
  - Tutorial 29.
- **Receipts: policy simulation (#114).** `agent-custody policy simulate --policy <proposed.cedar> --receipts <dir> --issuer-key …` and `simulatePolicy` replay recorded calls against a proposed Cedar policy.
  - **Trust:** every receipt is verified first, then replayed on its recorded arguments, facts, and grant.
  - **Report:** each changed decision is listed with its receipt id.
  - **Incomplete runs:** a call the replay cannot evaluate makes the run INCOMPLETE. That covers a gate refusal, withheld inputs, and an authorization whose receipt never arrived.
  - **Flags:** `--approval-key`, `--capture-key-env`, and a repeatable `--disclose`.
  - **Memory:** receipts stream one at a time.
  - Tutorial 28.
- **Receipts: other changes.**
  - **Report:** the verify report shows why a call was refused (`denied: delegation grant has been revoked`), or says the reason is withheld under a capture rule.
  - **Example 27:** revokes an agent's grant mid-session.
  - **Replay builder:** `scripts/replay.ts` packages example 27 and state example 07 as a folder of receipts and public keys that anyone can verify with the published packages.
- **State:** example 07 lists a call whose consumed beliefs are withheld under a capture rule as INCOMPLETE in a blast radius. With the customer's key, the same query finds the call.
- **Site:** the landing page leads with the local refund demo and shows its six steps (#117).
- **Release and deploy:**
  - **Automatic publish:** a version tag publishes the packages from CI (`release.yml`, trusted publishing, once `PUBLISH_FROM_CI` is `true`). The log image and the MCP Registry listing follow only after the release succeeds, so the image is never built before its package exists.
  - **Manual deploy:** `deploy/upgrade.sh` upgrades the log's host to a published version and rolls back if the new one is not healthy, or with `docs` rebuilds the docs site. The `deploy` workflow runs it over SSH, by hand, with a key that can run nothing else; see `deploy/README.md`.

## 0.7.0 — 2026-10-15

- **State:** `blast` and `loadReceipts` know what they cannot see: a receipt that withholds its consumed fact ids under a capture rule is listed under `withheld` (`INCOMPLETE` in the report) rather than counted as having relied on nothing, and `--capture-key-env` / `loadReceipts(dir, { captureKey })` decrypts the ids of receipts in mode `encrypted`; `explain` says when the beliefs shown are withheld.
- **Receipts:** private evidence (issues #109, #76, #126). `capture` in the gateway and SDK configs says, per tool or `"*"`, what the receipt file carries of the arguments, the result, and the facts: `clear` as before, `digest` keeps the fields listed in `clear` and withholds every other top-level field as one salted sha256 commitment at `$rest` (so that field names, which the agent or the upstream chose, never appear either), `encrypted` does the same and carries the object under a 32-byte key from the environment variable `captureKeyEnv` names (AES-256-GCM; a rule in that mode without the key fails at startup). The rule is applied in one place: `createIssuer` takes `capture: { rules, key }` and `privateView` turns the whole predicate into the statement it signs, the authorization included, before the log and the exporters see it. Once any side is private, a side the rule does not set is withheld whole, and so is every value that is not structural (policy error messages, a denial reason, a thrown message, the result's `_meta`, a provider delivery's body, a field added later), in the rule's mode; a fixed list stays in clear (the receipt id, key ids, timestamps, the host's session and model ids, the tool, the grant, the digests, the decision and policy ids, the status, the provenance fields, a provider's signature and bind path, the note); a provider's delivery body, an upstream's signed envelope, the result's `_meta`, and the consumed fact ids are upstream-authored and withheld under any private rule, beside a clear result too. On a result `isError` stays in clear and `_meta` never does. The policy decides on the real values; the agent gets the real result, error, and reason; the digests and the signature are over the whole call, and no salt is in the receipt: a commitment is `{ $custody: "withheld", sha256 }`, its salt kept by the issuer in `receipts/salts/<id>.json` (0600 in a 0700 directory, pruned with the receipt) for a digest-only commitment, or inside the ciphertext with the value for an encrypted one, and nowhere else; `request.argsDigest`, `execution.resultDigest`, and each fact's `resultDigest` are salted from the salts of the values withheld under them. So nothing in the receipt confirms a guess of a withheld value (#126; the dictionary regression in `test/capture.test.ts` runs in both modes). A disclosure carries `{ $custody: "disclosed", salt, value }` at each path, as `reveal` writes it; a value without its salt is refused, and so is a salt without its value, which `reveal --include-salts` writes for the holder to complete and never by default. The salts file is written 0600 in a 0700 directory and pruned with the receipt. A verifier skips an upstream check only for a part the signed note declares withheld (vector `gateway-undeclared-envelope-commitment-resigned`), and both verifiers require string hash fields (vectors `sdk-array-hash-commitment-resigned`, `sdk-array-keyid-commitment-resigned`). One function, `effectiveRule`, selects a call's rule for the gateway and the issuer alike; beside a result left in clear an envelope that is exactly the plain attestation for this call stays (every envelope and signature-entry field checked, canonical bytes, bound to this receipt, tool, and result) and a withheld one fails the upstream check (vector `resigned-clear-result-envelope-withheld`); the upstream checks run beside a clear result whose only withheld part is `_meta` (vectors `gateway-private-clear-result-upstream-attested`, `gateway-private-clear-result-upstream-wrong-key`); a key that is not a commitment's fails the checks naming the key id; the browser checks iv and tag lengths (vector `gateway-private-short-tag-resigned`); a note head that is a prototype member fails instead of throwing (vector `resigned-note-path-proto`); a fact argument named `$rest` is an argument; `loadReceipts` skips authorization files; `explain` opens the explained receipt's consumed ids with the key and prints the beliefs it opened. The provider's bound value must appear in what the agent received, never in the delivery's copy in `_meta` (vector `resigned-provider-bound-value-missing`); for a tool no upstream offers the issuer combines the name's rule and the wildcard side by side, the more private mode and only the fields both keep in clear; the issuer checks the salts directory before signing and keeps an authorization's view until the log took the receipt; `reveal` fails on a foreign key; the Splunk event never carries a commitment; `explain` and the packs report withheld consumption as `INCOMPLETE` and take `--capture-key-env`; a note naming a path twice, `execution.upstream` whole, or `execution.result.isError` is refused. An encrypted commitment is bound to its receipt and path (AES-GCM additional data), `reveal` takes `--issuer-key` and verifies the bundle before decrypting, writes `--out` owner-only and never through a symlink; both verifiers run `structural parts in clear` first, refusing a note that is malformed or names a structural part, and a statement whose status, tool, grant, or digests are not what the checks read (five vectors); a provider's signature and bind, the session and model ids, and a tool name no upstream offers are withheld under a private rule (the rule is selected by the real name, the view shows `(unknown tool)`), `consumed` is shared with the authorization, `prune` removes the authorization file, the issuer writes salts after the log append and lets an authorization's view go after an hour, the key is accepted in strict hex or base64 only, and an encrypted commitment needs a 12-byte iv and a 16-byte tag. A fact's `resultDigest` is a commitment to the lookup's full result under a private rule (disclosed, decrypted, and checked at `withheld facts.<name>.resultDigest`), since the receipt shows only the selected value and the rest of the result is private whatever the selected fields are; a producer that does not pass the full result gets the digest string withheld; `reveal --out` writes owner-only and chmods an existing file; a result's `isError` stays in clear only when it is the boolean flag; a tool or fact named like an inherited property (`constructor`) is looked up by own property; a receipt id from a bundle or a log line is checked before it becomes part of a path; the issuer keeps an authorization's view only once the log has taken it, bounded, and builds the receipt's view on it rather than withholding the shared parts twice. An upstream's signed envelope is withheld with the result, since its payload may carry any claim; a commitment is recognised only when well formed (vector `sdk-malformed-commitment-resigned`); the OTLP span's status message is a fixed string where the error is a commitment.
