# Changelog

All three packages, `@agent-custody/receipts`, `@agent-custody/state`, and `agent-custody` on PyPI, move in lockstep. The receipt format has stayed at v0.2 throughout; every addition to it is an optional field, so earlier receipts and the published conformance vectors remain valid.

## 0.16.2 — 2026-11-09

- **Test coverage in CI, and a pull request template.** `bun run coverage` runs the receipts and state tests with v8 coverage (`@vitest/coverage-v8` 5.0.0) and the Python tests with `pytest-cov`, then prints the totals per package and the least covered files. The new `coverage` job in the test workflow runs it on every pull request and on main, writes the summary to the job summary, and uploads the HTML reports as an artifact. It is not a required check. Coverage counts only code that runs in the test process, so the CLI, which tests run as a child process, shows as uncovered. Every pull request now uses `.github/pull_request_template.md` (what and why, how it was tested, a checklist of the repository's rules, notes for the reviewer), and the `pr-template` workflow fails while a section is missing or empty. Dependabot's pull requests pass it, so it can be a required check. `pytest-cov` 6.0.0 is pinned in the Python `test` extra, so `uv.lock` owns its tree, and a failed artifact upload never fails the coverage job.
- **The log lock reads its owner stamp once per process.** The lock that keeps the writers of one log in order records its owner's start time, so that a later process with the same PID is not taken for the owner. `takeLock` read it on every append, and on macOS, which has no `/proc`, every read ran `ps`: about 1.1 ms of a 1.3 ms append. A process's start time cannot change while it runs, so `ownProcessStamp()` in `operations.ts` reads it once, for the lock and the operation store, and tries again on the next call when a read failed (the operation store used to keep a failed read). The lock record is unchanged. On an Apple M5 a log append went from a mean of 1276 µs to 160 µs, and the site's full gateway call from 2.1 ms to 0.7 ms; [docs/performance.md](packages/receipts/docs/performance.md) has the numbers. `test/lock-stamp.test.ts` fails if the lock reads the stamp again for each append.
- **A cheaper receipt hot path, measured.** `evaluate()` passed the Cedar policy text to `isAuthorized` on every decision, so Cedar parsed the whole file each time, and hashed it each time for the digest. It now parses each policy text once with cedar-wasm's `preparsePolicySet` and decides with `statefulIsAuthorized`. The cache is keyed by the text, so an edited file is a new parse and a new digest. It holds 8 policy sets and evicts the least recently used. A new text takes a slot id that no live entry holds, and the eviction, which frees the evicted entry's id for reuse, happens only after the new set is in place, so cedar-wasm holds at most 9 sets. A preparse that throws (cedar-wasm throws for policies that are not text, and on a trap) returns its slot and changes no live entry, so a live entry always decides with its own text (`test/policy-cache.test.ts`). A text that does not parse is a deny with Cedar's errors, as before, and is never evaluated against the set its slot held before. Reserved Cedar forms in arguments are still refused first, and diagnostics still become reasons and errors. The local Merkle log kept calling `appendFileSync`, which opens and closes the file for each leaf. It now keeps one descriptor open for append. It reopens the file when the path names another file (a prune renames a new file into place) or no file, and after a failed write. The torn-tail repair is unchanged, and `O_APPEND` puts each line after the cut. `MerkleLog.close()` releases the descriptor; a log that is dropped without it releases it when it is collected. What is fsynced is unchanged: neither the old nor the new append fsyncs the log. A new script, `bun run bench` in `packages/receipts` (`scripts/hot-path-bench.ts`, not part of `ci`), times each step of one receipt: the Cedar decision, the receipt signature, the log append with its Merkle part, the tree-head signature, and a Rego decision beside the Cedar one. Rego already compiled once per change, so it needed no change. [docs/performance.md](packages/receipts/docs/performance.md) has the numbers and what they leave out. On macOS most of a log append is the lock: its owner record carries the process start time, which `ps` supplies there because there is no `/proc`.

- **An OWASP Agent Control Standard (ACS) Guardian, as a spike.** ACS is a JSON-RPC wire contract: an agent asks a Guardian before it acts. Its baseline signature is an HMAC both sides hold, so a Guardian's decision is not attributable to the Guardian (ACS §8.6), and its trace events are self-reported until a party outside the runtime attests to them (the ACS Trace README). **`agent-custody acs --config acs.json`** reads a `steps/toolCallRequest` or `steps/toolCallResult` (or a batch) on stdin and answers allow or deny by the Cedar policy. Each decision is a receipt with the new issuer kind `guardian`, signed with the Guardian's key, appended to the log, and returned in `policy_data["agent-custody"]`. The agent, the tool, and the arguments are `claimed`; the decision is `observed`; an allow is `withheld`, since a Guardian forwards nothing. An `acsStep` fact carries the ACS `request_hash` and the `chain_hash` (§8.2), which the answer also publishes. A result whose `request_id_ref` the Guardian cannot resolve is recorded as unresolved. A repeated `request_id` is refused (`-32005`), including two concurrent calls: the calls of one session are decided one at a time, so the chain cannot fork. A session belongs to the `agent_id` that opened it, and another agent naming it is refused (`-32000`). On a result, `context.acs.requestRef` carries the request's decision, tool, agent, and `consumed`, so a policy can let one result through, for the tool that was allowed. The example policy refuses `..` in a path. The policy file is re-read when it changes; a changed file that does not parse is refused and the one in force stays. A receipt that cannot be written means no decision (`-32603`). The CLI exits 1 when any answer is an error. Only a decision is receipted, and the verifiers do not recompute the `acsStep` chain links; `docs/acs.md` says both, and that trust is by issuer key, not by kind. `createAcsGuardian(cfg).handle(message)` is the same with no transport. **All three verifiers** know the kind and check `guardian receipt carries a policy decision` and `guardian decided, executed nothing`; four vectors (`guardian-*`, `resigned-guardian-*`) are appended to `vectors/receipts.json`, and the existing vectors are unchanged. **Not implemented**, listed in `docs/acs.md`: the handshake, ACS request and response signatures, the other 17 hooks, `modify`/`ask`/`defer`, provenance, the timestamp skew window, Intent, Rego, an HTTP or framed stdio transport, Trace, and Inspect. **ACS issue #18** (an audit chain that rests on one Guardian) proposes three directions; `docs/acs.md` maps them: a `chain_hash` signed under a long-lived key and exported as a checkpoint (done: the receipt bundle), signed heads in an external append-only log (done: the log, run by someone else, with `--log-key`, `audit`, and the witness), and Guardians exchanging chain heads (not done). Example 43 shows the first and the last against a log under a separate key. The ACS README's sample request goes through as is, and its answer validates against the ACS response schema. Docs: `docs/acs.md`, `site/reference/acs.md`, the receipt spec's `issuer.kind` row. Example 43.

- **The egress witness: detect, refuse or allow, and receipt the calls that go around the gateway.** Until now, an agent with a credential in its own environment could call a provider directly, and only `completeness` caught it, after the fact and for Stripe only. **Lockdown comes first**, because a proxy alone is advice: an agent can ignore `HTTPS_PROXY`. `deploy/gateway/lockdown` has a Kubernetes NetworkPolicy that gives agent pods default-deny egress except the gateway, the witness, and the cluster DNS. It runs the witness beside the gateway, with a NetworkPolicy of its own that refuses private ranges and the metadata address. The docker compose equivalent is an override with an internal network. The new guide page `site/guide/credential-custody.md` says that tool credentials live only in the gateway, and how to lock down and test egress. The `gateway-image` workflow checks both manifests. **`agent-custody egress`** is an HTTP forward proxy that relays CONNECT and plain HTTP, with no TLS interception. It identifies each agent only by its own proxy credential (`Proxy-Authorization: Basic`, secret from the environment, compared in constant time), never by what the agent declares. A connection without a valid credential is refused with 407 in every mode. The Cedar policy decides per destination, with the action `host:port` and the witness's own `destination` fact in context. Each connection, relayed or refused, gets a signed receipt with the new issuer kind `egress`: the agent, the destination (observed), the address connected to, the times, the bytes each way, how it ended, and the outcome. Receipts go to the log like any other. Before any byte moves, it commits the connection to the log as an authorization, as the door does for a request that can change something. A log that refuses means nothing is relayed (503), and a killed witness still leaves the open on record. A host name is never dialled at an internal address: the resolver the socket connects with drops loopback, private, shared, link-local and metadata addresses (`169.254.169.254`, `192.0.0.192`), multicast, and reserved space, in IPv4, IPv6, IPv4-mapped, and NAT64 form. An IP literal is dialled only when the policy names it. A CONNECT host is made canonical by the same URL parser as a plain request's, so an IPv4 address written in octal, as one number, or in hex (`010.0.0.1`, `2130706433`, `0x7f.1`) is decided on as the address it names, and an IPv4 part with a leading zero is not an address in any of the three verifiers. It follows the door's limits: an in-flight cap answered 503 without a receipt, connect and idle timeouts, and no client-written address header believed. A plain request is relayed without the proxy credential, with `Host` set to the destination the policy decided on. Stopping the witness closes and receipts every open connection, including one still committing or connecting. A receipt is an observed bypass, not a record of what was done. A witness that is killed leaves the committed open in the log, but no closing receipt with the byte counts. Lockdown ships for Kubernetes and docker compose only; the guide says how to build it on a VM, bare metal, or a cloud task. The root README has a section with an animated diagram (`site/public/egress-witness.svg`). - **Egress lockdown for agents on a Linux VM or bare metal.** `deploy/gateway/lockdown/vm` is a shipped recipe beside the Kubernetes and docker compose ones, where the guide used to describe only the mechanism. `agent-lockdown.nft` is an nftables table that matches the agent's Unix user (`meta skuid`): whatever that user runs reaches only the gateway on 8790 and the witness on 8791, and everything else, loopback and the DNS resolver included, is logged and refused. The agent reaches both by address and the witness resolves every other name, so DNS, a channel the witness does not see, stays closed. Reloading it replaces only its own table. `agent-custody-lockdown.service` loads it at boot without `nftables.service`, whose stock `/etc/nftables.conf` starts with `flush ruleset` and would delete docker's and ufw's tables. `agent-lockdown.conf` is a systemd drop-in for the agent's unit. It requires that service, so an agent whose table fails to load stays down. A start or a reload of `nftables.service` also flushes the table. `nftables-lockdown.conf`, a drop-in for that service, loads the table again after each one, and stops the agent if that load fails. The agent's drop-in runs the agent as that user with `NoNewPrivileges` and `RestrictAddressFamilies=` (no vsock to the hypervisor), and sets `IPAddressDeny=any` with `IPAddressAllow=` for the gateway and the witness, so the unit stays locked down if the host firewall is flushed. That filter is by address only, since systemd has no port filter, so it allows no resolver either: an allow would open every port on it. `agent-custody-egress.service` runs the witness under a user of its own, with the same `egress.json` as the other recipes. It denies the witness the internal ranges from the witness's own address list, including the cloud metadata addresses and the benchmarking range, so a policy that permits a private IP literal is still refused. The guide says when a resolver in `/etc/resolv.conf` needs an allow: only when it names the VPC resolver directly, not the systemd-resolved stub. `check-lockdown.sh` runs the guide's three tests as the agent user, or inside the agent unit's filter with `--unit`, then opens a loopback port of its own and requires that the agent cannot reach it over IPv4 or IPv6. It reads the proxy secret from the agent's env file or `EGRESS_SECRET_FILE`, not the command line. The drop-in alone fails that check. Check 2 requires a new receipt that names the refused host and says denied. A direct connection must fail where the same connection as root succeeds, so a host with no route out cannot pass. A connection through the witness to a refused host must get 403 and a new receipt. The gateway must answer. The `gateway-image` workflow checks the files with `nft -c`, `systemd-analyze verify`, and shellcheck. A new `vm-lockdown` job installs the recipe on a fresh Ubuntu runner and runs the checks with no lockdown (they must fail), with the whole recipe, and with the drop-in alone. It also checks that loading the table leaves another table in place, and that the table comes back after a start and a reload of `nftables.service`. It checks that the agent stays down when the table fails to load, that the agent gets no answer from the resolver, that the agent's unit refuses vsock, and that the witness refuses a permitted private address.

- **Gateway: reload the Cedar policy without a restart (issue #145).** The gateway re-reads `policyFile` whenever it changes (device, inode, mtime, ctime, or size, and on each call while the file is under two seconds old), as it does `revokedGrants`, and evaluates the next call under the new policy, for stdio, HTTP, A2A, and observe mode, with no dropped session. - **Fix: `policy simulate` checks the receipt id against the file name.** A receipt copied over the file name of another receipt hid that call, counted the copy two times, and the report still said `COMPLETE`.
