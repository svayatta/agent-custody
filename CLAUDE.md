# Working in this repository

This is a Bun workspace. `packages/receipts` is the receipts package, `packages/state` is the governed-memory package. The root README lists packages and layout; each package has its own README. `bun run test`, `typecheck`, and `demo` at the root run across packages; the CLI and tutorials run from inside `packages/receipts`.

- **The READMEs must reflect every change before it is committed.** The package README for the package touched, and the root README when the layout or package list changes. In `packages/receipts/README.md` check, at minimum: the intro, the doc links, the supported hosts table, the quick start, the layout block, and the Plan section (move finished items to Done, renumber Next). Do not commit code that a README describes differently.
- The guides under `packages/receipts/docs/` are part of the change, not a follow-up. A new adapter, command, flag, or check gets documented in the same commit.
- Every Cedar example in `packages/receipts/docs/policies.md` is executed by `packages/receipts/test/docs-policies.test.ts`. Edit them together.
- Every file in a package's `examples/` is executed by that package's `test/examples.test.ts` and must end by printing `OK`. A new module or adapter gets an example in the same commit, plus a row in `docs/tutorials.md` for receipts.
- Consumers install compiled output. Each package has `tsconfig.build.json` emitting `dist/` with declarations and an `exports` map in its package.json; a new public module is added to `src/index.ts`, and a new adapter gets its own `./sdk/<name>` subpath. Pack with `bun pm pack`, not `npm pack`, so `workspace:*` dependencies are rewritten to versions. To release: bump the three versions and edit the two workspace `"version"` lines in `bun.lock` by hand, never with a blanket search-and-replace of the old version string, which once rewrote the `@electric-sql/pglite` pin (0.5.8) to a version that does not exist and hung `bun install --frozen-lockfile` silently; never delete and regenerate the lockfile, which re-resolves dependencies and has broken vitest before. To publish: bump the version, `bun run build`, `bun pm pack` in the package directory, then `npm publish <tarball> --access public` from a terminal with `NPM_TOKEN` set to a granular npm token that has the 2FA bypass; the gitignored project `.npmrc` reads it. Publish receipts before state, then run the `mcp-registry` workflow (Actions tab) so the MCP Registry entry in `packages/receipts/server.json` follows; bump its two `version` fields with the packages. `.github/workflows/release.yml` runs its check job on every tag; its npm and PyPI jobs run only when the repository variable `PUBLISH_FROM_CI` is `true`, which is to be set once trusted publishing is configured on both registries. The site page `site/security.md` is the vendor questionnaire; keep it true, every "no" a no, and date it.
- Framework adapters are tested against the real package with a scripted model and no network. Do not add an adapter with only a hand-written stand-in. The same rule holds for `packages/python`: its tests run with `uv run --extra test pytest` against a sidecar started from `packages/receipts/src/cli.ts`, and every receipt they produce is checked by the TypeScript verifier.
- `packages/python/agent_custody/crewai.py` wraps CrewAI tools by building a `CustodyTool` subclass instance that delegates to the original tool's `_run`; replacing `_run` on a pydantic tool instance does not take effect, which is why. The `crewai` extra is large; the test suite installs it.
- `packages/python` requires Python 3.10 (the `mcp` client needs it; both mcp 1.x and 2.x work); `agent_custody/memory.py` talks to the state package's HTTP memory server, whose tests need `bun run build` first, which `bun run test:python` does. The mcp Python result flag is `is_error`.
- `packages/receipts/examples/languages/<lang>` holds one complete sidecar client per language, run by `test/languages.test.ts` against a sidecar in its own process; a missing toolchain skips that language visibly. Tests that run a client synchronously must not host the sidecar in-process, or the client hangs.
- `src/sdk/openclaw.ts` (OpenClaw plugin hooks, typed loosely from openclaw's `hook-types.ts`, no dependency; `before_tool_call` blocks on deny after issuing the denial receipt and blocks too when the receipt cannot be issued; example 21 and `test/openclaw.test.ts`) and `packages/python/agent_custody/hermes.py` (Hermes Agent plugin: `pre_tool_call` block, `post_tool_call` record, `register(ctx)` entry; the drop-in directory is `packages/python/hermes-plugin/`, tested in `tests/test_hermes.py`) follow the Claude Agent SDK precedent: the documented hook contract, driven as the host drives it. Muse (muse.ai) is a connector marketplace with no hook surface; a connector provider fronts their own API with the gateway instead.
- Observe mode: `mode: "observe"` (optional in both config schemas; absent means enforce) makes the gateway and `createSdkIssuer` stamp `enforced: false` on every `PolicyDecision`; `denies(policy)` (TS in `sdk/index.ts`, Python in `agent_custody`) is the one test every adapter uses before blocking, so a recorded deny is never acted on. The gateway forwards on a not-enforced deny and prints, rather than withholds, when the log refuses a precommit authorization. `verify.ts`/`verify-web.ts` accept `deny (observe mode, not enforced) -> executed` and refuse the same receipt without the flag; vectors `gateway-observe-denied` and `resigned-observe-flag-stripped` pin it. `test/observe.test.ts` and `tests/test_observe.py` cover every layer.
- `src/sdk/deepseek-harness.ts` is itself a DeepSeek Harness plugin (`name`, `inject: ["tools"]`, `Config` as a zod schema because Cordis requires Standard Schema, `apply(ctx, config)`), listed by package path; `tools/pre-execute` returns `{ kind: "deny", reason }` or `next()`, never `allow`; `tools/post-execute` records then `next()`. Types mirror the harness's `packages/core/tools/src/index.ts` (`exec.name/arguments/callId/agent.session.header.id`, result `isError/content/value/error`); example 22 and `test/deepseek-harness.test.ts`. A post-execute for a tool the policy denies records deny+executed and fails verification, which is right: in the harness the pre gate runs first.
- Record-only adapters evaluate no policy. Enforce or observe, never both on one tool.
- `issue`, `record`, and `handleHookEvent` are asynchronous because the log may be remote. A log that refuses a leaf is an error and no bundle is written; never swallow it except where a framework cannot await, and then print it.
- Money is integer minor units; Cedar has no floats.
- The CLI runs on plain Node 22 via native type stripping: no parameter properties, no enums, `.ts` import specifiers. The state package imports the receipts package through its `exports` map, `@agent-custody/receipts` or `@agent-custody/receipts/sdk/<name>`, which resolves to `dist/`; the state typecheck and test scripts build receipts first, and running a state example by hand needs `bun run build` at the root.
- `packages/state/src/review.ts` renders `formatExplain` output as pages (`renderIndex`, `renderReceipt`, `serveReview`, `writeReview`); no auth of its own, loopback by default, CSP `default-src none`. Tested with a real gateway and an async CLI spawn.
- `packages/state/src/explain.ts` answers the ten questions for one receipt (`buildActionPack`, `formatExplain`, signed `ACTION_PACK_TYPE`); the ledger is optional and the belief questions then read "unknown without a ledger", never "nothing". `verifyActionPack` checks the receipt and every downstream receipt inside.
- `packages/state/src/pack.ts` builds the custody pack from the ledger and the receipts directory; receipts inside a pack still carry the values they recorded, by design, and the pack test asserts only that the fact itself is erased. `Store.verifyRemoved` is optional; a store without it is `unverified`, never `verified`.
- `CHANGELOG.md` gets an entry for every version bump, written when the bump commit is made, and the site renders it at /changelog.
- **main is protected**: every change lands by pull request, the `test` check must pass on the branch head and be up to date with main, force pushes and deletions are refused, and the rules bind administrators too. Wait for `gh pr checks --watch` before merging; a merge attempted before the check has registered is refused, not skipped.
- **Nothing is pushed to main until `bun run ci` has passed locally.** It runs exactly what the GitHub workflow runs: a frozen-lockfile install (a manifest change without `bun install` fails there), typecheck, every test suite, the site build, and the Python suite. `.githooks/pre-push` enforces it; enable it once per clone with `git config core.hooksPath .githooks`. Never gate a commit on a filtered test output (`bun run test | grep ...` reports grep's exit code, not the tests'); run the command bare and let it fail the step.
- Each package has a `vitest.config.ts` with a thirty-second test budget and a sixty-second hook budget, because tests spawn gateways and load PGlite; a timeout on a loaded machine is not a failure, and a test that needs longer says so in its own `it(..., ms)`. When a gate run and the pre-push hook run back to back, the second is under load; do not pack or build while either runs.
- Commit messages carry no attribution trailers.
- `packages/receipts/vectors/` are conformance vectors: regenerate with `bun run vectors` only when the receipt format or a check changes, and commit the result; never regenerate to make a failing test pass. `site/verifier/verify-web.ts` is the browser verifier and must keep passing every vector; when a check is added or renamed in `src/verify.ts`, mirror it there.
- `packages/state/src/stores.ts` `pgvectorStore` is tested in `test/pgvector.test.ts` against the `pgvector/pgvector:pg16` image in Docker, skipping visibly when no daemon runs; PGlite 0.5.8 has no pgvector. The `pg` optional peer is imported dynamically in that test only.
- `packages/state/src/stores.ts` also has `lettaStore` (real `@letta-ai/letta-client` against a stand-in of `/v1/agents/{id}/archival-memory`; custody travels as tags since passages have no metadata), `langgraphStore` (any LangGraph `BaseStore`, tested with the real `InMemoryStore`, one item per fact keyed by fact id), and `cogneeStore` (Cognee has no JS client, so the adapter is its own HTTP against `POST /api/v1/add` multipart, `GET /api/v1/datasets/{id}/data`, `DELETE …/data/{dataId}`; the add returns no id, so `put` lists the dataset and matches `external_metadata.factId`; tested against a stand-in of those routes only). Both client packages are dev dependencies.
- `packages/state/src/stores.ts` adapters are typed structurally (no runtime import of `mem0ai` or `@getzep/zep-cloud`); their tests use the real client packages against fake HTTP endpoints, with `MEM0_TELEMETRY=false` so the Mem0 client stays offline. Write order in the server is validate, stores, ledger; retract order is ledger, then stores.
- `packages/state/src/server.ts` reads `agent-custody/receipt`, `agent-custody/agent`, and `agent-custody/observed` from the call's `_meta`; the gateway sets them and the agent cannot. Keep the key strings identical in both packages; state duplicates them on purpose to avoid a runtime import.
- `packages/receipts/src/upstream.ts`: an upstream signs `{ receiptId, tool, contentDigest }` where contentDigest is over `{ content, isError }` only, never `_meta`. The browser verifier mirrors the check. The site's early-access form mails `partha@charioteerconsulting.com` unless `ENDPOINT` in `EarlyAccess.vue` is set to a form service.
- `packages/state/src/storage.ts`: `Ledger` is asynchronous and holds no events; it takes a path (JSONL, SQLite when it ends in `.sqlite`/`.db`, a `postgres://` URL) or an `EventStore`. `selectAbout`/`selectFor` are the reference semantics of the two pushdown queries and the SQL stores must match them; the ledger suite runs on JSONL, SQLite, and Postgres (PGlite in-process) via `describe.each`, so a store change is wrong if any backend diverges. SQLite is loaded with `createRequire` so JSONL users never import `node:sqlite`, and the SQLite store migrates the pre-0.2 schema on open. `pg` is an optional peer dependency loaded with `createRequire` only for URLs; `PostgresStore` never closes a client it was given. Forget then `compact()`: SQLite checkpoints the WAL, Postgres runs `VACUUM FULL` unless `vacuum: false`; sweeps compact once at the end. Warehouses are export targets, not stores.
- `packages/receipts/src/otel.ts` exports one OTLP/HTTP JSON span per receipt (trace id = receipt id, no OpenTelemetry SDK dependency); `createIssuer(..., { exporter })` calls it after the bundle is written and swallows failures, so a collector is never on the evidence path. `otel` is an optional block in both config schemas. `packages/receipts/src/splunk.ts` is the same shape for a Splunk HTTP Event Collector (`splunk: { url, tokenEnv, index?, source?, sourcetype?, host? }`, token from the environment at startup); `openExporter` fans out to every configured exporter, each told independently.
- `packages/receipts/src/rest.ts` is the REST connector: an `{ rest: { baseUrl, headerEnv, tools } }` upstream implements the `UpstreamClient` subset of the MCP client, so the gateway treats it like any upstream. Header secrets come from the environment at startup; tests run it against a `node:http` stand-in API, never the network.
- `packages/receipts/src/gateway.ts` is a host (`createGatewayHost`: key, policy, issuer, upstreams, fact lookups) plus `open(grantEnvelope)` sessions, each with its own delegation and consumed facts; `createGateway` is one session for `grantFile`, which is optional in the config. `src/gateway-http.ts` (`serveHttp`, `gateway --http`) serves a host over Streamable HTTP with a session per connection, the grant presented base64url in `Authorization: Bearer` or `X-Agent-Custody-Grant` on initialize; untrusted or expired grants get 403 with the reason before any session exists (not 401, which the MCP client transport treats as an OAuth challenge). Tested with two concurrent MCP clients.
- `precommit` in the gateway config lists consequential tools (or `*`). For those, `issuer.authorize` signs and logs an authorization statement (`AUTHORIZATION_PREDICATE_TYPE`, written as `<id>.authorization.json`) before the call is forwarded; if the append fails the call is `withheld` and nothing goes upstream. The receipt embeds the authorization bundle and `verifyBundle` runs five `authorization ...` checks, mirrored in the browser verifier and pinned by the `gateway-precommit-*` vectors. `createGateway(cfg, { log })` accepts a sink for tests.
- `packages/receipts/src/delegation.ts`: a grant may carry `agentKey` (SPKI PEM) and `parent` (the envelope it was delegated from); `delegateFrom(parent, agentKey, sub)` signs a child, `verifyDelegation` walks the chain (max depth 4) and returns the leaf as `delegation`, the root principal keyid as `keyid`, and `chain`; `verify.ts` adds "delegation chain to the principal" only when a parent is embedded, mirrored in `verify-web.ts` (`verifyDelegationChain`) and pinned by the `gateway-chain-*` vectors. CLI: `grant --agent-key`, `delegate`.
- Provider deliveries (`ProviderAttestation`) share the `_meta["agent-custody/upstream-signature"]` slot with DSSE envelopes; `upstreamEvidenceOf` tells them apart. Secrets reach `verify` only through `--stripe-secret-env` / `--github-secret-env`, never as flag values. The fake Stripe attaches webhooks with `--webhook-secret`.
- A pruned log line is `{"pruned":"<leaf hash hex>"}` and a hash-only appended line is `{"hash":"<hex>"}`; `MerkleLog` reads both as the hash. `httpLog(..., { hashOnly })` sends `{ leafHash }`; the server accepts `{leaf}` or `{leafHash}`, serves tenant logs at `/t/<tenant>/…` from `--tenants`, and writes `log` into tree heads from `--log-id`; `verifyBundle`/`auditExtends` check it when given `logId`, mirrored in the browser verifier and pinned by the `remote-log-*-id` vectors. The receipts package exports `./cli` so the state CLI can spawn the gateway for `sweep --via`. Forget digests: `sha256` (default), `hmac-sha256` with a forget key held outside the file, or `none`.
- `packages/receipts/src/signer.ts` and `checkpoints.ts`: `logHandler`/`serveLog` take a `KeyPair` or a `Signer`; `localSigner` wraps a key, `connectSigner` talks to `serveSigner` (`POST /sign` with a shared token, `GET /keys` public). The log serves `/.well-known/agent-custody-log.json` (current key first, retired after) and `fetchLogKeys` backs `--log-url`. `CheckpointPublisher.publishOnce` signs one head per grown log into a `CheckpointStore` (`dirCheckpoints`, `postgresCheckpoints`, `bothCheckpoints`); `/checkpoints?since=` lists them. The entrypoint runs the signer with `ROLE=signer`.
- `packages/receipts/src/log-store.ts`: `LogBackend` is the async face of a log; `fileBackend` wraps `MerkleLog`, `PostgresLog` keeps hashes per tenant with an advisory lock per append and resyncs its subtree cache when the table moved on; single-connection clients (PGlite) have their transactions queued per client. `PostgresTenancy` holds tenants and sha256-hashed tokens; `logHandler` takes a file or a `LogResolver` (`fileResolver`/`postgresResolver`) and applies `RateLimiter` per token and a body cap. Tests run on PGlite. `pg` is an optional peer loaded with `createRequire` in the CLI only; the image installs it.
- Per-address limits (`RateLimiter` keys for tokenless appends and admin failures) use `clientAddress(req, trustProxy)`: the socket address unless `--trust-proxy` (`TRUST_PROXY=1` in the container, set by compose because Caddy fronts it), in which case the first `X-Forwarded-For` address. Never default it on.
- `packages/receipts/src/log-export.ts` is a tenant's self-service export (`log-export`): `GET /t/<tenant>/leaves?since=&limit=` and `/usage?month=` answer only to that tenant's token; `LogBackend.leafHashes(from, to)` backs it; the export self-checks (head and checkpoints against the published keys, leaves against the roots) and writes `log.jsonl` in the verifier's log-copy format. `deploy/backup-offsite.sh` rclones the backup directory to `BACKUP_REMOTE`.
- `packages/receipts/src/log-check.ts` is the monitor (`checkLog`, `log-check`), run by `.github/workflows/monitor.yml` every ten minutes against the live log; `PostgresTenancy.usage(month)` backs `/admin/usage` and `/admin/usage.csv`; `GET /health` is liveness only.
- `packages/receipts/src/witness.ts`: `Witness.runOnce` fetches the log's key document, each watched tenant's `latest.json` checkpoint, verifies it, checks consistency against `state.json`, and `dsseCountersign`s it into `<out>/<tenant>/`; refusals write `ALARM.json`. `auditExtends(..., { witnessKeys })` requires a witness signature (mirrored in the browser verifier). `deploy/witness/` is a separate stack (`ROLE=witness`); it must not run on the log operator's machine.
- Plans: `log_tenants.plan` (`free` default, `team`, `enterprise`; `PLAN_QUOTAS` 10k / 1M / none per calendar month, overridable per `PostgresTenancy` for tests via `quotas`), `setPlan` audited as `tenant.plan`, `quota(id)` cached ten seconds with `noteAppend` keeping it honest; the append route answers 429 with `retry-after` to month end when the allowance is used; `/t/<t>/usage` and `/admin/usage` carry `plan` and `quota`; admin page has a plan select; CLI `log-admin tenant plan`.
- `packages/receipts/src/portal.ts` is the tenant portal (`portal` CLI, `ROLE=portal`, compose service `portal`, Caddy at `PORTAL_HOST`): `PortalStore` (`portal_users` scrypt, `portal_members`, `portal_billing`), signed-cookie sessions (`PORTAL_SECRET`, `SameSite=Strict`, writes need JSON), registration is two steps: `/api/register` with email and password creates the account (with tenant/name/company as well it does everything in one call, for scripts), `/api/onboard` takes the profile (`Profile`: name and company required, role, phone, telegram optional; `portal_users` columns added with `ADD COLUMN IF NOT EXISTS`) and the tenant id (filled in from the company name on the page, log URL previewed; `__LOG_BASE__` and `__PROVIDERS__` replaced at serve time) and creates the tenant and first key with actor `portal:<email>`; `/api/me` returns `tenant: null` until then and the page shows the onboarding screen. Provider sign-in (`OAuthOptions`, GitHub and Google over fetch, `portal_identities`, state in a signed ten-minute `custody_oauth` cookie, callback answers with a page whose own navigation carries the Strict session cookie; Google's id token is read unverified because it arrives from Google's token endpoint in the exchange), dashboard reads the tenancy and `log_heads`, `setupFor(tenant, logId)` is the welcome sheet as data (`setup` on register and overview) rendered as numbered steps at registration and under Setup, `MailOptions` sends a welcome (never the key) and an operator note through Resend's HTTP API off the request path (stand-in `fetch` in tests; `deliverMail` is the shared sender), and `sendFollowUps` (CLI `portal-followup`, `deploy/followup.sh` as `/etc/cron.hourly/agent-custody-followup`) sends `founderNote` once to registrations an hour to a week old, marking `portal_users.followed_up_at`, skipping the operator's own mail domains, Stripe over REST (`stripeRequest`, `verifyStripeSignature` on `Stripe-Signature`), webhook moves plans as `stripe:<event>`, never touching an enterprise tenant. Tested with PGlite, a live log beside it, and a Stripe stand-in.
- Published policies: `PostgresTenancy.addPolicy/listPolicies/policy/policyByDigest/removePolicy` (`log_policies`, unique per tenant and digest, digest = `sha256Hex(text)` = the gateway's `policyDigest`), audited as `policy.add`/`policy.remove`; `GET /t/<t>/policies` (the tenant path regex in `log-sink.ts` whitelists operations, add new ones there), `policies.json` in the export, portal `/api/policies[?digest=]`, `/api/policies/<id>[/remove]`, and the Policies page with the match tool. The gateway never reads them.
- `PostgresTenancy` writes an audit row (`log_audit`: actor, action, tenant, detail, never a token) on every `addTenant`/`disableTenant`/`addToken`/`revokeToken`, with the `by` argument the caller passes: the admin routes pass `admin:<basic user or bearer>@<address>`, the CLI passes `cli:<user>@<host>`, and a missing actor is recorded as `unattributed`. `tenancy.audit({tenant, limit})`, `GET /admin/audit`, the page's Activity section, `GET /t/<tenant>/audit` with the tenant token, and `audit.json` in the export read it.
- `packages/receipts/src/log-admin.ts`: `adminRoutes` gates everything under `/admin`, the page included, on the admin token presented as HTTP Basic (browser prompt) or bearer, throttles failures per address, and serves one inline page (CSP `default-src none`, stores nothing) plus the `/admin/*` JSON API, behind `--admin-token-env`, Postgres mode only; `welcomeSheet` is the same text `deploy/onboard-tenant.sh` prints. The same surface is served at the root of `ADMIN_HOST` by a Caddy rewrite (root → `/admin`, other paths prefixed, `/admin/...` passed through). `registrations(tenancy, portal, month)` joins `PostgresTenancy.usage` with `PortalStore.registrations` (read only, same database) for `/admin/registrations[.csv]` and the page's Registrations section with its totals; the log CLI passes `portal: new PortalStore(client)`. Never put an admin token in a transcript; tests mint their own. The portal and admin pages are TypeScript template literals: a quote inside the page's own JavaScript strings is written `\\"` in the source, and each test compiles every inline `<script>` with `node:vm`, because one `\"` once shipped a blank page (0.6.8, 0.6.9).
- `deploy/RUNBOOK.md` is the operator's runbook (upgrade, backups, restore drill, token and tenant lifecycle, key rotation, leaked secrets, what each monitor failure means); the entrypoint lists every `/data/keys/retired/*.pub` as a retired key for the signer. `SECURITY.md` at the root is the disclosure policy. Every outbound fetch in the receipts package carries an `AbortSignal.timeout`; `httpLog` takes `timeoutMs` (config `log.timeoutMs`, default 10 s).
- `deploy/stripe-setup.sh` runs on the server with `STRIPE_SECRET_KEY` in `.env`: python3 against Stripe's REST API creates or reuses the Team product, the $50/month price, and the webhook endpoint, and writes `STRIPE_PRICE_TEAM` and `STRIPE_WEBHOOK_SECRET` into `.env`; it prints ids, never a secret.
- `deploy/onboard-tenant.sh` runs on the server: `log-admin tenant add` + `token add`, token kept in `/root/agent-custody-tenants/<id>.token` (never printed into a transcript), and prints the welcome sheet. The early-access page now says the log is running and taking three tenants; keep it honest about the witness not existing.
- `deploy/` runs the reference log server as a container: the Dockerfile installs the published `@agent-custody/receipts` (pinned by `AGENT_CUSTODY_VERSION`), the entrypoint generates the key on first start, and `docker-compose.yaml` and `k8s/` share one environment-variable contract (`AGENT_CUSTODY_LOG_FILE|KEY|PORT|TOKEN`). Profiles `public` (Caddy TLS) and `phase2` (Postgres, unused until issue #6 phase 2) are off by default; their variables must stay optional so `docker compose config` passes without them. Check with `docker compose -f deploy/docker-compose.yaml config -q` and `kubectl kustomize deploy/k8s`. The site excludes `deploy/**`. `.github/workflows/image.yml` pushes the image to ghcr.io on a `v*` tag or by hand (`gh workflow run image.yml -f version=X`); it uses `GITHUB_TOKEN`, never a personal token, and builds each architecture on a native runner (`ubuntu-24.04-arm` for arm64) then merges the digests into one tag, because npm under QEMU emulation dies with SIGILL.
- `.claude/settings.json` registers `.claude/custody-hook.sh` on PreToolUse, PostToolUse, and PostToolUseFailure; it records only on a machine with `~/.config/agent-custody/hook.sh` (SDK config, key, Cedar policy, receipts, and the tenant token, all outside the repo) and exits quietly elsewhere. Receipts go hash-only to tenant `agent-custody` on the hosted log. The policy forbids force pushes and `rm -rf /`. `site/custody.md` shows it; `site/public/custody/` holds sample receipts, the public key, and the policy.
- `site/reference/` is the reference documentation, served at docs.agent-custody.dev (the same site build, the `docs` compose service built by `deploy/docs.Dockerfile` from the checkout on the log host, `deploy/update-docs.sh` after a pull) and at agent-custody.dev/reference/. Every function, endpoint, and tool has its request and response there, written by hand because TypeDoc does not support the workspace's TypeScript 7; a new or changed public function, route, MCP tool, or CLI flag updates the matching reference page in the same commit.
